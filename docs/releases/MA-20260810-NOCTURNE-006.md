# Nocturne Self-Hosted Migration Maturity Audit

## Evaluation context

This audit covers the full migration of the accepted Nocturne public catalogue
and single-operator Attendance Alpha from the former hosted identity and D1
runtime to a self-hosted production chain. The target environment is a public
friend-facing site with an independently protected shop admin. Booking,
payments, customer identity, payroll, staff role expansion and broader content
publishing remain outside scope.

Target stage: self-hosted friend-facing production Alpha with a protected
single-operator attendance admin. Stage readiness is 3 of 3 because the code,
standalone artifact, process supervisor, proxy authentication, SQLite
migrations, DNS, TLS, public routes, protected routes and rollback evidence all
passed their applicable release gates.

`Version 035a8d9 / Overall Maturity L3 within the self-hosted public catalogue and single-operator Attendance Alpha / Evolution Capability E4 / Confidence high`

## Overall conclusion

The release is suitable for the declared public Alpha and single-operator admin
scope. Public access, proxy authentication, application authorization, local
persistence, migration execution, process supervision, TLS, DNS and rollback
evidence are integrated across the production chain.

The overall level remains L3. Release-time verification is strong, while real
attendance usage and recurring monitoring are still absent. Those gaps limit a
claim of adaptive production maturity.

## Decision impact

Release the self-hosted version and retire the former hosted path from active
DNS. Preserve the old hosted deployment and exact DNS snapshot as the rollback
boundary. Keep staff expansion and additional business functions blocked until
operating policy, offboarding and recurring health evidence exist.

## Topology and critical path

Friend request → DNS and TLS → Caddy public route → loopback Node → catalogue
or published attendance projection.

Operator request → Caddy Basic Auth → trusted proxy marker → application access
check → same-origin command policy → attendance state machine → SQLite
transaction and audit event → published-only public projection.

Release chain → tested commit → versioned standalone artifact → `current`
pointer → LaunchAgent → local health → managed Caddy site → DNSHE cutover → TLS
issuance → public smoke → receipt and rollback snapshot.

The critical production chain is closed for the declared scope. The weakest
remaining link is recurring external observation after release.

## Change quality, risk and debt

变更类型：缺陷修复、结构优化、闭环补全、系统能力提升；依据：本次发布移除了造成朋友与店铺人员访问障碍的托管身份和数据库耦合，并建立了经本番验证的独立认证、持久化、部署与回滚链路。

Major risks and controls:

1. Shared Caddy changes can affect other local services. Candidate validation,
   managed-site isolation and reload health checks limit this risk.
2. Two old A records required coordinated replacement. Both were backed up and
   updated, and five resolvers were verified.
3. Certificate issuance initially encountered failed-authorization limits
   because DNS still pointed to the old host. DNS rollback remained available;
   issuance succeeded after the old TTL and issuer retry window expired.
4. A single shared access code is acceptable only for the current operator
   boundary. It must not silently expand into multi-staff identity.
5. SQLite is appropriate for the current single-host, low-concurrency scope.
   Backup and recovery need stronger evidence before the database contains
   operationally important history.

## Evolution capability

E4 is supported within this migration by a complete controlled-update loop.
The reported login defect was recorded, diagnosed as a hosted identity and
runtime coupling problem, converted into a migration decision, implemented,
tested, released with rollback, interrupted by a real port conflict, corrected
through evidence, and revalidated through public production smoke. The new
website-development rule prevents recurrence of the original hosting mistake.

## Next gate

1. Record the first real attendance create-to-publication task and verify the
   anonymous projection.
2. Add a lightweight recurring check for public health and certificate expiry.
3. Create a recoverable SQLite backup after the first real record and perform a
   restore test before the history becomes operationally important.
4. Define named staff roles, access revocation and offboarding before sharing
   admin access beyond the current single-operator scope.
