# Nocturne Operations Foundation Maturity Assessment

## Evaluation context

This assessment covers the accepted D0 operations workflow probe and its
production release as an inert foundation. The public catalogue remains
read-only. Production requests to `/admin` return 404, and no database,
authentication, upload or production write path exists.

The target of the next stage is a narrowly controlled internal operations
alpha covering authentication, durable attendance state and deterministic
review. Sites supports route-scoped Sign in with ChatGPT while leaving public
content anonymous. The Human Owner's requirement that friends can view the
public catalogue without a ChatGPT account therefore remains compatible with
an authenticated `/admin` route.

`Version c120795 / Overall Maturity L2 within the public catalogue and inert admin foundation / Evolution Capability E4 / Confidence high`

## Overall conclusion

Sites version 5 is suitable for the existing public catalogue because the
public routes and supplied photographs are unchanged, the production admin
route fails closed, and the prior Sites version remains available for rollback.

The operations workflow is mature enough for D0 product validation. It is not
qualified for real staff use. Authentication, durable audit, data recovery,
concurrency and production writes have no implementation evidence.

## Decision impact

Release the accepted inert foundation to production while retaining Sites
version 4 as the immediate rollback boundary. Continue the next slice only in
an isolated development branch. Do not expose `/admin` or create D1-backed
writes until route-scoped SIWC and an explicit server-side owner allowlist are
implemented and tested.

## Topology and critical path

Human Owner acceptance → validated commit → `main` fast-forward → production
build and tests → Sites version 5 → custom-domain HTTP checks → worker error
log check → release receipt.

The release chain is closed. The next-stage chain begins at identity:

SIWC identity → server owner allowlist → attendance command → D1 transaction
→ review → public schedule projection → cancellation or rollback.

The weakest link is the unimplemented owner authorization boundary between
SIWC identity and D1-backed write commands.

No later node should be promoted to production until the identity and
authorization boundary is supported and tested.

## Change quality, risk and debt

变更类型：结构优化、闭环补全、系统能力提升；依据：本次变更把已验收的后台流程、状态门禁、回滚与下架约束固化为生产失效关闭的代码和自动化测试，同时没有开放新的生产入口。

The additional source increases repository size and maintenance surface, while
runtime risk remains bounded because the production page fails closed before
rendering the admin client.

Remaining risks:

1. A future developer could weaken the production 404 before authentication is
   ready.
2. Attendance domain rules have not been confirmed against real operations.
3. Future multi-staff identity and offboarding rules are unresolved.
4. Durable audit, migrations, backup and recovery have no evidence.

## Next gate

Implement route-scoped SIWC with an explicit owner allowlist, document the
attendance state machine and add a D1-backed development slice with isolated
data. The exit evidence is one authorized submission, one independent review,
one public schedule projection, one cancellation, one conflict rejection, one
unauthorized-access rejection and one recovery test without exposing customer
information.
