# Nocturne Cast Access Maturity Assessment

## Evaluation context

This assessment covers the isolated development candidate that adds named cast
accounts, cast-owned attendance drafting, administrator review, account
enablement and disablement, access-code rotation, session invalidation and an
append-only identity event history. The intended users are individual cast
members and the existing store operator. The target environment remains the
self-hosted Nocturne Alpha.

Booking, customer identity, payment, payroll, published-schedule revisioning,
password recovery, multi-store tenancy and production deployment are outside
this assessment. Production remains on the prior baseline while this candidate
awaits Human Owner acceptance.

Target stage: accepted production candidate. Stage readiness is 2 of 3 because
the domain, implementation, migration, automated tests and browser workflow
have passed, while production secret injection, database backup, deployment,
health smoke and rollback verification remain pending.

`Version codex/feature/cast-schedule-access / Overall Maturity L3 within the isolated cast access and attendance-review candidate / Evolution Capability E4 / Confidence medium-high`

## Overall conclusion

The candidate closes the requested role-separation chain in development. Cast
members can change and submit only their own attendance. Administrators can
review, reject, approve, publish and cancel, while account administration is
kept in a separate protected view. Permission checks live in the server-side
domain and store path, so browser UI changes cannot expand authority.

Overall maturity is L3 within the stated development scope. The domain model,
database schema, sessions, APIs, UI and audit records are integrated and have
repeatable tests. The production interface remains deliberately open, which
prevents a production-readiness claim.

## Decision impact

Continue with controlled Human Owner validation. Keep the production domain,
Caddy configuration, production SQLite file and process supervisor unchanged.
Production promotion requires explicit acceptance followed by the existing
release gates.

## Topology and critical path

Store operator → protected admin route → cast account create or reset → scrypt
credential hash → one-time temporary code → cast sign-in → signed HttpOnly
session → active-account and session-version check → cast-bound attendance draft
→ submit → administrator approve or reject → administrator publish → anonymous
published-only projection.

Disable or rotate → account session-version increment → next request reads current
account → earlier cookie rejected.

The development critical path is closed. The weakest interface is candidate to
production: production secret injection, SQLite backup and migration, process
restart, proxy routing for `/staff`, smoke evidence and rollback receipt are
still pending.

## Change quality, risk and debt

变更类型：功能扩张、闭环补全、结构优化、系统能力提升；依据：本次修改将单一管理员代办出勤扩展为女孩自助提交、管理员独立审核、身份撤销与会话失效的完整权限链路，并用数据库、接口、界面和测试共同约束。

1. New account, session and API components increase the system surface, but
   they directly support the requested separation of duties and remain bounded
   by one account per profile.
2. Credential plaintext is returned only during create or reset. The database
   stores a scrypt hash and rotating a credential invalidates earlier sessions.
3. Login throttling is process-local. This is acceptable for the isolated
   Alpha candidate and remains a scaling debt.
4. Published attendance cannot be edited by cast members. Supporting that
   policy safely requires a separate revision model and remains intentionally
   deferred.
5. The development database and QA access code are disposable test state and
   must not be copied into production.

## Evolution capability

E4 is supported within this development change by one complete controlled
update loop. The missing role capability was recorded and converted into a
domain and permission model. Implementation and migration followed. Automated
tests verified role separation and session invalidation. Browser review found
an access-page status mismatch, a six-item mobile navigation issue and a Vinext
prefetch compatibility error. Each issue changed the implementation, passed
regression checks and received a fresh runtime verification.
